## 1. 图像编码 — 格式与原理的博弈

### 1.1 OpenCV 支持的编码“全家桶”

在 OpenCV 中，图像编码不仅仅是调用 `cv::imwrite` 那么简单。作为一个计算机视觉库，OpenCV 的核心任务是处理像素矩阵，而文件的读写（I/O）实际上是依赖于外部编解码库的。理解 OpenCV 支持哪些编码，实际上是在理解它背后集成了哪些第三方库。

#### 1.1.1 OpenCV 内置的核心格式

OpenCV 的源码中内置了对几种基础格式的编解码器，这意味着无论你在 Windows、Linux 还是 Mac 上编译 OpenCV，这些格式通常都是默认可用的，不需要额外安装系统级依赖。

1. **Windows 位图 (\*.bmp, \*.dib)**

- 特点：==无压缩或简单的 RLE 压缩==。
- 原理：**直接存储像素矩阵的原始数据（RGB/BGR）**。
- **OpenCV**：读取速度极快，因为没有复杂的解压算法，但文件体积巨大。
- **应用场景**：通常用于调试或临时数据交换。

2. **便携式图像格式 (\*.pbm, \*.pgm, \*.ppm, \*.pxm, \*.pnm)**

- 特点：==极简的 ASCII 或二进制格式==。
- 原理：文件头直接定义宽、高和最大像素值。
- 应用场景：**在早期**的计算机视觉研究和学术实验中非常流行，因为解析极其简单，甚至可以用文本编辑器直接修改图片内容。

3. **Sun Raster (\*.sr, \*.ras)**

- **特点**：Sun Microsystems 工作站的遗留格式，现在较少见，但 OpenCV 依然保持支持。

#### 1.1.2 主流压缩格式（依赖第三方库）

这部分格式是实际开发中的主力军。OpenCV 通过 CMake 配置，在编译时会自动下载并静态链接这些库（或者链接系统已有的库）。

4. **JPEG (\*.jpg, \*.jpeg, \*.jpe)**
   - **底层依赖**：==libjpeg / libjpeg-turbo==
   - **编码类型**：有损压缩。
   - **OpenCV 特性**：支持 8 位和 12 位精度。支持基线 JPEG 和渐进式 JPEG（Progressive JPEG，网页加载时从模糊变清晰的效果）。
   - ==注意==：理论上 OpenCV 会自动旋转，但为了保险起见，我们在做人脸检测或 OCR 时，最好手动处理 EXIF 信息，或者确保你的 OpenCV 版本是最新的。

5. **PNG (\*.png)**
   - **底层依赖**：==libpng / zlib==
   - **编码类型**：无损压缩。
   - **OpenCV 特性**：支持 8 位和 16 位深度（灰度或彩色）。支持 Alpha 通道（透明度）。
   - ==注意==：OpenCV 默认读取 PNG 会丢弃 Alpha 通道（变为 3 通道 BGR），如果需要保留透明度，必须使用 cv::IMREAD_UNCHANGED 标志。

6. **TIFF (\*.tiff, \*.tif)**
   - 底层依赖：==libtiff==
   - 编码类型：灵活容器（支持 LZW, JPEG, PackBits 等多种压缩方案）。
   - 应用场景：**医学影像（支持 32 位浮点数据）**。**高动态范围图像**。**多页文档扫描**。
   - **OpenCV 特性**：OpenCV 对 TIFF 的支持非常强大，能够读取高位深数据，这在工业视觉检测中非常重要。

7. **WebP (\*.webp)**
   - 底层依赖：==libwebp==
   - 编码类型：支持有损（基于 VP8 视频帧）和无损。
   - **现状**：Google 推出的格式，压缩率优于 JPEG 和 PNG。OpenCV 4.x 版本开始全面支持 WebP 的读写，非常适合网络传输场景。

#### 1.1.3 特殊与高清格式

8. **JPEG 2000 (\*.jp2)**
   - 底层依赖：==OpenJPEG（推荐）== 或 JasPer（已弃用）。
   - 特点：基于小波变换，支持无损压缩，没有 JPEG 的“马赛克”效应。
   - 现状：虽然技术先进，但因为专利和计算复杂度问题，普及度不如 JPEG。

9. **OpenEXR (\*.exr)**
   - 底层依赖：==OpenEXR==
   - 特点：工业光魔开发的 HDR 格式，支持 16/32 位浮点像素。
   - 应用：电影特效渲染、高动态范围成像。

10. **Radiance HDR (\*.hdr, \*.pic)**

- **特点**：经典的 HDR 格式，==OpenCV 内置支持==，常用于光照估计任务。

#### ==1.1.4 支持不佳的格式（避坑指南）==

1. **GIF (\*.gif)**

- 现状：OpenCV **不支持直接读取** GIF 动画。
- 原因：GIF 涉及多帧动画和复杂的调色板索引，且专利历史遗留问题导致 libgif 集成复杂。
- 解决方案：读取 GIF 请使用 imageio 或 Pillow 库，转为 numpy 数组后再交给 OpenCV 处理。

2. **HEIC / HEIF (\*.heic)**

- 现状：**iPhone 的默认照片格式**。OpenCV 默认不支持。
- 解决方案：需要依赖 libheif，或者先用系统工具转为 JPEG。

3. **RAW 格式 (\*.cr2, \*.nef)**

- **本质**：RAW 不是一个具体的文件格式（像 .jpg 那样），它是指“传感器原始数据”。相机的 RAW 叫 .CR2 / .NEF，手机的 RAW 可能是 .DNG，甚至工业相机的 RAW 就是纯二进制数据。
- **OpenCV 的态度**：OpenCV 的 imread 不支持 直接读取这些 RAW 数据，因为它不知道怎么“显影”。

==所以，OpenCV 的图像编码支持可以概括为：**“内置基础格式，外挂主流格式”**。==

- 做**算法调试**：首选 BMP 或 PNG（无损，无压缩伪影）。
- 做**网络传输/存储**：首选 JPEG（体积小）或 WebP（体积小且新）。
- 做**工业/医学检测**：首选 TIFF（高位深支持）。

切记：遇到 GIF 或 HEIC 格式，不要硬用 `cv::imread`，否则只会得到 None。

### 1.2 图像的诞生：从光子到矩阵的奇幻漂流

在我们讨论 **JPEG 怎么压缩** 之前，我们先得搞清楚一个终极问题：**这张图最初是怎么来的？** 当我们按下快门的那一瞬间，现实世界的光影是如何变成电脑里那个由 0 和 1 组成的矩阵的？这个过程其实是一场精密的物理与数学的接力赛。

#### 1.2.1 捕捉光线：传感器的“马赛克”世界

一切始于镜头后的那块图像传感器（CMOS 或 CCD）。你可以把它想象成一片由几千万个微小“水桶”组成的田地。

- **光电转换**：当光线（光子）射入，这些“水桶”（感光二极管）会根据光的强弱产生不同量的电荷。光越强，电荷越多。

这里有一个反直觉的事实：==传感器其实是“色盲”==。传感器上的每个像素点只能感知**光的强度（亮度）**，而不能感知颜色。为了获得颜色，工程师在每个像素点上盖了一个滤光片。最常用的是==拜耳阵列==。

- **拜耳阵列的“偏科”**：50% 的像素盖了**绿色**滤镜（因为人眼对绿色最敏感）。25% 盖了**红色**。25% 盖了**蓝色**。

**此时的状态**：传感器输出的原始数据，是一张只有 ==单通道亮度信息== 的马赛克图。每个像素只知道“这里很亮”或者“这里很暗”，并且只知道自己应该是红、绿、蓝中的某一种。

#### 1.2.2 模数转换：跨越物理与数字的鸿沟

传感器产生的电荷是**模拟信号**（连续的电压值）。计算机看不懂电压，它只认识 0 和 1。这时候，**模数转换器**登场了。

- **采样与量化**：
  - ADC 会测量每个像素点的电压高度，并将其转化为一个数字。
  - 如果是 12-bit 的 ADC，它会把电压映射为 0~4095 之间的整数。
  - 如果是 14-bit，则是 0~16383。

此时我们得到了一堆巨大的数字矩阵。但这堆数字依然不是我们眼中的“照片”，它被称为 **RAW 数据**。

#### 1.2.3 ISP：相机的“大脑”与“化妆师”

RAW 数据虽然保留了最完整的信息，但它很难看：灰暗、充满噪点、颜色也是残缺的（因为每个像素只有一种颜色）。这时候，**图像信号处理器**接管了工作。它是相机或手机里的专用芯片，负责把“生肉”（RAW）烹饪成“佳肴”（RGB 图像）。它主要做了三件大事：

- ==黑电平校正==：即使在完全黑暗的环境下，传感器也会有微弱的电流（热噪声）。ISP 会把这些“底噪”减掉，确保纯黑的地方真的是黑色。

- ==去马赛克（最关键的一步）==：对于那个只记录了红色的像素点，ISP 会通过算法，参考它周围绿色和蓝色像素的数值，“猜”出这个点原本应该有的绿色和蓝色值。通过这种插值算法，原本只有单通道信息的 RAW 数据，变成了每个像素都有完整 RGB 三个数值的矩阵。

- ==白平衡与色彩校正==：人眼很聪明，在黄光灯下看白纸，依然觉得它是白的。但传感器很笨，它会如实记录成黄色。ISP 需要通过算法，把这种色偏“拉”回来，让白色物体在任何光线下都显示为白色。

此时经过 ISP 处理后，我们终于得到了一个标准的、色彩鲜艳的 **RGB 数字图像矩阵**。这就是 OpenCV 读取后得到的那个 `numpy.array`。

#### 1.2.4 分岔路口：保存为位图还是压缩格式？

- 路径 A：直白存储。直接把矩阵里的每一个数字（R、G、B）原封不动地写入硬盘。
- 路径 B：数学压缩。在写入硬盘前，先对这个矩阵进行数学变换（DCT、量化、熵编码），把重复的、人眼看不出的信息扔掉。

### 1.3 JPEG 深度解析：有损压缩的艺术

JPEG 之所以能成为互联网上最主流的图像格式，核心在于它在“文件体积”和“视觉质量”之间找到了一个近乎完美的平衡点。它不像 PNG 那样追求像素级的完美复刻，而是选择了“欺骗”你的眼睛——丢弃那些你根本注意不到的细节。

这种“欺骗”并非胡乱丢弃，而是基于严谨的数学变换和人眼视觉特性。JPEG 的压缩流程可以概括为三个关键步骤：**色彩分离**、**分块与变换**、**量化**。

#### 1.3.1 色彩分离：欺骗人眼的 YCrCb

我们在之前的章节提到过，人眼对**亮度**（明暗）的敏感度远远高于对**色度**（颜色）的敏感度。如果你把一张彩色照片变成黑白，你依然能看清大部分细节；但如果你把颜色保留，把细节模糊掉，画面就会变得难以辨认。

JPEG 利用了这个特性，在压缩前，会先将图像从 **RGB 色彩空间** 转换到 **YCrCb 色彩空间**。

- **Y (Luma)**：亮度分量。代表图像的明暗细节。
- **Cr (Chroma Red)**：红色色度分量。代表像素偏离灰色的红色程度。
- **Cb (Chroma Blue)**：蓝色色度分量。代表像素偏离灰色的蓝色程度。

转换完成后，JPEG 会执行一个关键操作：==色度抽样==。通常的做法是保留所有的 Y 分量（亮度），但把 Cr 和 Cb 分量（颜色）的数据量减少一半。

这意味着，原本 3 个通道的数据，现在变成了 1.5 个通道的有效数据。**仅仅这一步，文件体积就凭空减少了 50%，而人眼几乎看不出任何区别**。

#### 1.3.2 分块处理：化整为零

处理完颜色后，JPEG 不会一次性处理整张图片（那计算量太大了），而是将图像切分成无数个 **8x8 像素的小方块**。

为什么要切成 8x8？这是一个工程上的权衡。块太小，压缩效率低；块太大，计算复杂且容易出现“方块效应”。8x8 是 JPEG 标准制定者经过大量实验得出的“黄金尺寸”。

#### 1.3.3 量化：有损压缩的“刽子手”

这是 JPEG 压缩中最关键、也是唯一“有损”的一步。在量化之前，数据会先经过一个叫 **DCT（离散余弦变换）** 的数学工具处理。你不需要懂复杂的公式，只需要知道 DCT 的作用：**它把 8x8 的像素矩阵，从“空间域”转换到了“频率域”**。

- **空间域**：记录的是“这个像素是红色的，那个像素是蓝色的”。
- **频率域**：记录的是“这个块是平滑渐变的（低频），还是剧烈变化的（高频）”。

转换后，8x8 的矩阵左上角代表**低频信息**（图像的大致轮廓和颜色），右下角代表**高频信息**（图像的边缘、噪点和细节）。量化的过程，就是用一个预设的量化表去除 DCT 变换后的系数。

- 对于左上角的低频系数，量化表给的步长很小，保留大部分细节。
- 对于右下角的高频系数，量化表给的步长很大，甚至直接归零。

结果：原本复杂的 8x8 矩阵，经过量化后，右下角变成了一堆 0。在计算机里，连续的 0 是最容易压缩的。这就是 JPEG 有损的本质：它认为人眼看不出那些高频细节，所以把它们扔掉了。

#### 1.3.4 压缩方法：最后的打包

经过量化后，数据已经变得非常“稀疏”（充满了 0），这时候再进行无损压缩，效率极高。

1. DCT（离散余弦变换）
   如前所述，DCT 是 JPEG 的核心数学引擎。它将图像信号分解为不同频率的余弦波。虽然听起来很复杂，但你可以把它理解为一种“特征提取”——它把图像中最本质的特征（低频）和次要特征（高频）分离开来，为后面的“丢弃”做准备。
2. 熵编码：哈夫曼编码
   这是 JPEG 压缩的最后一步，也是完全无损的一步。
   经过量化和“之字形扫描”（把 8x8 矩阵变成一维数组，让 0 排在一起）后，数据流中充满了大量的 0 和重复的数值。
   哈夫曼编码登场了。它的原理很简单：
   给出现频率高的数值分配短的二进制编码。
   给出现频率低的数值分配长的二进制编码。
   这就像摩斯密码一样，常用的字母（如 E）用短码（.），不常用的字母（如 Q）用长码（--.-）。通过这种方式，JPEG 在不损失任何信息的前提下，进一步压榨了文件体积。

#### 1.3.5 OpenCV 实战：掌控压缩的艺术

- 保存原理（流程切入）：
  _ 色彩分离：为什么要把 RGB 转成 YCrCb？（利用人眼对亮度敏感、对色度不敏感的特性）。
  _ 分块处理：将图像切分为 8x8 像素块。\* 量化：这是“有损”的关键。解释如何通过丢弃高频细节来减小体积。
  - 压缩方法：
    - DCT（离散余弦变换）：简单带过，说明它是把图像从“像素空间”搬到“频率空间”的工具。
    - 熵编码：哈夫曼编码（Huffman Coding），最后一步的“打包”压缩。
  - OpenCV 实战：
    - 演示 cv::IMWRITE_JPEG_QUALITY 参数（0-100），展示 90 和 10 的文件体积与画质肉眼对比。

### 1.4 PNG 深度解析：无损与预测

- 保存原理：\* 滤波（Filtering）：这是 PNG 的核心。解释“差分编码”思想——存“当前像素与左边像素的差值”比存“像素本身”更容易压缩。
  - 压缩方法：
    - DEFLATE 算法：LZ77 + 哈夫曼编码。简单解释“查找重复字符串并替换”的逻辑。
  - OpenCV 实战：
    - 演示 cv::IMWRITE_PNG_COMPRESSION 参数（0-9），说明 PNG 压缩是“用 CPU 时间换空间”。

## 2. 视频编码 — 时间维度的压缩魔法

视频就是“会动的图片”，但压缩逻辑完全不同，重点在于利用“时间冗余”。

### 2.1 视频编码的“黑盒”与“白盒”

- 常见编码标准：H.264 (AVC)、H.265 (HEVC)、MPEG-4、MJPG。
- 容器与流：MP4、AVI、MKV 只是盒子，里面装的才是 H.264 等编码流。
- OpenCV 的后端：说明 OpenCV 的 VideoWriter 其实是调用了 FFmpeg 或系统自带编解码器。

### 2.2 视频压缩的核心原理：I、P、B 帧

- I 帧（关键帧）：就是一张完整的 JPEG 图片。
  - P 帧（前向预测）：只存“跟上一帧不一样的地方”。
  - B 帧（双向预测）：参考前后帧，压缩率最高。
  - GOP（图像组）：解释 I 帧的间隔，间隔越大体积越小，但拖动进度条越卡。

### 2.3 OpenCV 视频编码实战

- FourCC 码：解释 'XVID', 'MJPG', 'H264', 'AVC1' 这些四字代码的含义。

## 3. 前沿视野 — SOTA 与 下一代技术

### 3.1 从 H.265 到 VVC (H.266)

- 趋势：在同等画质下，体积越来越小，但对算力要求越来越高。
- AV1 编码：开源、免专利费，正在成为互联网视频的主流（B站、YouTube 都在用）。

### 3.2 AI 赋能的压缩（Neural Compression）

- AI 超分：传输低分辨率视频，播放端用 AI 脑补成 4K（如 NVIDIA Maxine）。
- 生成式压缩：不再传输像素，而是传输“语义指令”，由接收端 AI 重绘画面（这是非常前沿的方向）。

## 2. 图像压缩

仍旧记得，在我刚开始写博客的时候，因为有很多图像需要插入网页，我就想做一个编写的批量压缩图像的小软件。但是那个时候，我 OpenCV 用不明白，只能用 Pillow 进行压缩操作。所以，我来弥补遗憾了！

当然了，并不是说 OpenCV 做压缩就一定更好，它只支持 JPG、PNG、BMP、WebP 等主流格式，而 Pillow 支持更多格式，包括 TIFF、GIF、ICO 等。对比 OpenCV 和 Pillow：

- 如果需要更高性能和复杂图像处理任务，比如物体检测或图像分割，选择 OpenCV。
- 如果主要是格式转换、批量处理或 Web 图片压缩，选择 Pillow 更轻便。

如果是高性能需求，可以在 OpenCV 中处理图像，再使用 Pillow 保存成其他格式或更进一步优化。

### 2.1 imwrite 中的压缩参数

```py
import cv2

image = cv2.imread('img_process_0/lena.png')

cv2.imwrite('img_process_0/compressed1.jpg', image, [cv2.IMWRITE_JPEG_QUALITY, 50])
cv2.imwrite('img_process_0/compressed2.png', image, [cv2.IMWRITE_PNG_COMPRESSION, 9])
cv2.imwrite('img_process_0/compressed3.webp', image, [cv2.IMWRITE_WEBP_QUALITY, 50])
```

- **IMWRITE_JPEG_QUALITY**：设置 JPEG 的压缩质量，范围为 0 - 100（默认值 95）。值越大，图像质量越高，压缩率越低，文件越大。值越小，图像质量下降，压缩率越高，文件越小。

- **IMWRITE_PNG_COMPRESSION**：设置 PNG 图像的压缩等级，0 - 9（默认值为 3）。值越大，压缩率越高，文件越小，但压缩速度越慢。值为 0 时不压缩，为 9 时压缩率最高但速度最慢。

- **IMWRITE_WEBP_QUALITY**：设置 WebP 图像的压缩质量，0 - 100（默认值为 75）。支持有损和无损压缩。值越大，质量越高，文件越大；值越小，质量越低，文件越小。

OpenCV 中，压缩相关的较全的图像格式，以及压缩参数，见下表：

| 格式 | 参数名称                               | 压缩类型  | 参数范围   | 默认值 |
| ---- | -------------------------------------- | --------- | ---------- | ------ |
| JPEG | cv2.IMWRITE_JPEG_QUALITY               | 有损压缩  | 0 - 100    | 95     |
| PNG  | cv2.IMWRITE_PNG_COMPRESSION            | 无损压缩  | 0 - 9      | 3      |
| WebP | cv2.IMWRITE_WEBP_QUALITY               | 有损/无损 | 0 - 100    | 75     |
| TIFF | cv2.IMWRITE_TIFF_COMPRESSION           | 无损/有损 | 1, 2, 3, 5 | 无     |
| PXM  | cv2.IMWRITE_PXM_BINARY                 | 无损      | 0 或 1     | 1      |
| EXR  | cv2.IMWRITE_EXR_TYPE                   | 无损压缩  | 0 - 5      | 无     |
| JP2  | cv2.IMWRITE_JPEG2000_COMPRESSION_X1000 | 有损压缩  | 0 - 1000   | 无     |

### 2.2 使用对象保存压缩数据

使用对象保存压缩数据，储存到内存缓冲区，可以用 imshow 读取，也可以进行网络传输。

```py
import cv2
import numpy as np

# 根据实际大小自动选择合适的单位
def format_size(size_bytes):
    if size_bytes < 1024:  # 小于 1KB
        return f"{size_bytes} B"
    elif size_bytes < 1024**2:  # 小于 1MB
        return f"{size_bytes / 1024:.2f} KB"
    else:  # 大于 1MB
        return f"{size_bytes / (1024**2):.4f} MB"

# 读取原始图像
image = cv2.imread('img_process_0/lena.png')

# 将图像压缩为 JPEG 格式并保存到内存缓冲区
encode_param = [cv2.IMWRITE_JPEG_QUALITY, 50]  # 设置压缩质量为50%
result, buffer = cv2.imencode('.jpg', image, encode_param)

# 确保编码成功
if result:
    byte_size = len(buffer)  # 获取字节大小
    print(f"Compressed size: {format_size(len(buffer))}")
else:
    print("Compression failed")

# 可以将 buffer 转换为字节流
# 用于 网络传输、数据库存储、实时处理（比如imdecode）
compressed_bytes = buffer.tobytes()

# 从压缩的字节数据中重新加载图像
compressed_image = cv2.imdecode(np.frombuffer(compressed_bytes, np.uint8), cv2.IMREAD_COLOR)

# 显示解码后的图像
cv2.imshow('Compressed Image', compressed_image)
cv2.waitKey(0)
```

**（1）result, buffer = cv2.imencode(ext, img, params=None)**

1. 返回值 result：布尔（bool）类型，表示编码是否成功。如果成功，返回 True，否则返回 False。
2. 返回值 buffer：numpy.ndarray 类型，表示编码后的二进制数据，存储在一个字节数组中，可以直接用于传输或写入文件。

- 参数 ext：文件扩展名（例如：.jpg, .png, .webp），确定使用哪种编码格式。
- 参数 img：输入的图像数据（通常为 numpy 数组类型）。
- 参数 params：编码参数列表，用于控制压缩质量或算法选项。

**（2）retval = cv2.imdecode(buf, flags)**

1. 返回值 retval：解码后的图像，类型为 numpy.ndarray。如果解码失败，返回 None。

- 参数 buf：numpy.ndarray 或 bytes 格式数据。
- 参数 flags：控制解码后的图像格式和颜色空间，常用值有：

| Flag                               | 用途                                                    | 使用频率 |
| ---------------------------------- | ------------------------------------------------------- | -------- |
| cv2.IMREAD_COLOR                   | 彩色图像解码（默认方式，无透明度）                      | 高       |
| cv2.IMREAD_GRAYSCALE               | 灰度图像解码                                            | 高       |
| cv2.IMREAD_UNCHANGED               | 保持原始图像格式，包括透明度                            | 较高     |
| cv2.IMREAD_ANYDEPTH                | 处理高精度位深度的图像，如 16 位或 32 位                | 中等     |
| cv2.IMREAD_REDUCED_COLOR_2/4/8     | 彩色图像按比例缩小，适合大图像加载优化（1/2，1/4，1/8） | 中等     |
| cv2.IMREAD_REDUCED_GRAYSCALE_2/4/8 | 彩色图像按比例缩小，适合大图像加载优化（1/2，1/4，1/8） | 中等     |

### 2.3 压缩算法简介

OpenCV 中 ==JPEG== 压缩算法的核心技术是：==DCT (离散余弦变换)==：

1. 将图像从空间域转换到频率域，通过抛弃高频信息（细节）来减少数据量。
2. 量化步骤会进一步降低精度并减少存储需求。
3. 使用熵编码（Huffman 编码）最终压缩数据。

OpenCV 中 ==PNG== 压缩算法的核心技术是：==DEFLATE 算法==：

1. 使用无损压缩，包括 LZ77 和哈夫曼编码的结合。
2. 数据不会丢失，但文件大小会更大。

OpenCV 中 ==WebP== 压缩算法的核心技术是：==预测编码 + 熵编码==：

1. 使用预测编码来减少冗余数据，然后使用 VP8 编码进一步压缩。
2. 支持有损和无损模式，适合现代网页和移动端应用。
